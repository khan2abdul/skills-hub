How “auto-approved” actually works

A skill has no approval flag of its own. dsh decides approval from the session permission preset, not from the skill: read-only asks before every write, workspace-write asks before writes outside the workspace, and danger-full-access never asks. This profile runs danger-full-access with approval: never, so no skill triggers a permission prompt here.

What a skill can do is carry its own written gate: a step that tells the agent to stop and get your consent before a destructive or irreversible act. Those are marked stop and ask below, and it is the only per-skill approval signal that exists. Everything else is the preset's call.

All 42 are auto-invocable: no skill sets disable-model-invocation, so the agent may load any of them without being told to. You can also call any one by name, e.g. /ship-it.

This is the whole non-bundled catalog. The retired 5-stack roots are unconfigured: D:/repo/setupskills/active_skills (the addyosmani, caveman, gstack and legacy repos) and ~/.agents/skills (ponytail) are gone from discovery, and includeDefaultRoots: false keeps them out. dsh's own 12 bundled skills — the office* set, the three cordis authoring skills, agent-experience, diagnose-windows-sandbox-acl — are still enabled and are not listed here, because they ship with the harness rather than this hub.

Always on 3 skills

Apply on every task, not at one point in the pipeline.

trim-my-output

auto-invocable stops and asks rating 9.7 / A

Terse caveman-voice replies that keep every technical fact, code, path and number verbatim; stays on until "stop caveman" or "normal mode".

When to use it

  • The user types /caveman or says "caveman mode", "be brief" or "less tokens"
  • Every output token is billed and read in a terminal
  • The answer needs to lead with the result, with ceremony and hedging removed
  • A long session should stay compressed until the user says "normal mode"
  • Routine tool runs need one-line status instead of narration

When not to use it

  • A security warning or irreversible action is involved; break the rules and use plain prose, confirming in full sentences first
  • Anything persisted outside chat (code, comments, commits, docs, issues, PRs, tickets, memory files) must stay plain
  • Step order could be scrambled by a fragment, or the user is confused or repeating the question
  • The user asks for /caveman ultra or /caveman wenyan; those route to the ultracave or megacave skill

How to use it

"/caveman" → the agent answers first in terse plain sentences, keeping code, paths, numbers and errors verbatim.

Stops and asks: Irreversible actions require confirming in full sentences before proceeding, and security warnings drop the terseness.

write-less-code

auto-invocable rating 9.7 / A

Lazy senior dev mode: smallest complete change that solves the task, shortest working diff, no unrequested abstraction, plus a reply a busy human reads once.

When to use it

  • Any coding task: writing, fixing, refactoring, reviewing, choosing dependencies
  • The user says ponytail, be lazy, simplest solution, or yagni
  • The user complains about over-engineering or bloat
  • A vague build request needs the smallest version that does the core job
  • Deciding whether a new dependency or abstraction is warranted

When not to use it

  • Being smaller would mean cutting validation at trust boundaries, error handling that prevents data loss, security, accessibility, or something the user asked for
  • The user explicitly wants options, flexibility, or extensibility nobody has asked to skip
  • The work is a spec, plan, or prose document rather than a coding change

How to use it

"/write-less-code add retry to the upload call" → the agent greps callers, reuses the existing retry helper, and changes one call site.

Does not interrupt: Ultra level pushes back on the request before building, but no destructive action needs approval.

route-to-the-right-skill

auto-invocable rating 9.7 / A

The parent skill. Every other skill is a phase it routes to: check for an applicable skill before you act, say which one you are using, and re-route when the phase changes, two attempts fail, the scope moves, or you are about to claim done.

When to use it

  • Starting a session, before the first tool call
  • Crossing a phase boundary: spec approved, review passed, tests green
  • Two attempts on the same problem have failed, so it is a debug problem now
  • The user changes what they want and the spec is stale
  • About to say done, fixed or works
  • About to run a destructive or scope-expanding command
  • Unsure which of the 42 skills applies, or whether any does

When not to use it

  • Never skip it: the check is compulsory even when its conclusion is that no skill applies
  • It is not the work itself. If it is the only skill you used, you routed and never arrived
  • Not a substitute for reading the skill it names: routing without reading is the failure it exists to prevent

How to use it

"Fix the login redirect bug" → the agent checks for a skill, names the phase (Debug), says "Using debug-this-code", reads that file, and re-checks once the fix lands, which is Verify → prove-it-works.

Does not interrupt: No approval gate of its own. It hands you to the skill that has one: guard-the-dangerous-stuff before a destructive command, review-the-plan before code.

Understand 2 skills

Turn a vague ask into a shared, explicit intent.

interview-me-properly

auto-invocable rating 9.7 / A

Interviews the user one question at a time, each with a guess, until ~95% confidence, then restates intent for an explicit yes.

When to use it

  • The ask is missing who, why, what success looks like, or the binding constraint
  • The request is conventional ("build me X", "make it faster") and needs unpacking
  • The user says interview me, grill me, or stress-test my thinking
  • You catch yourself about to fill in ambiguous requirements before any plan, spec or code

When not to use it

  • The ask is unambiguous and self-contained (rename a variable, fix a typo)
  • The user explicitly asked for speed over verification
  • Pure information requests such as how does X work, or mechanical renames, formats and file moves
  • Non-interactive contexts: CI pipelines, scheduled runs, /loop, autonomous loops

How to use it

"/interview-me-properly build me a dashboard" → the agent states a one-sentence hypothesis with a confidence number, then asks one question with its guess attached.

Does not interrupt: No destructive action, but it requires an explicit yes on the restated intent before any spec, plan or downstream tool call.

discuss-on-new-idea

auto-invocable rating 9.7 / A

Refines a vague idea through divergent variations, convergent assumption stress-testing, and a one-pager with an explicit Not Doing list.

When to use it

  • Idea is still vague and needs shaping before it can become a plan
  • You want options expanded before converging on one
  • You want assumptions attacked before they become a plan
  • User says ideate, refine this idea, or stress-test my plan
  • A one-pager with MVP scope and a Not Doing list is the deliverable

When not to use it

  • The user is unsure what they want at all — use interview-me
  • A direction is already chosen and needs a spec — use spec-driven-development
  • The task is fixing existing behaviour rather than shaping a new idea

How to use it

"Help me refine this idea: an internal wiki" → the agent restates it as a How Might We, asks 3-5 sharpening questions, then proposes variations.

Does not interrupt: Nothing destructive is gated.

auto-invocable rating 9.7 / A

When to use it

Spec 3 skills

Write down what will be built and why, before code exists.

write-the-spec

auto-invocable stops and asks rating 9.7 / A

Turns intent into a gated, executable spec covering objectives, commands, structure, code style, testing, boundaries and success criteria before any code is written.

When to use it

  • Starting a new project or feature
  • Requirements are ambiguous or incomplete
  • The change touches multiple files or modules
  • You are about to make an architectural decision
  • The task would take more than 30 minutes to implement
  • One request bundles several independently testable capabilities and needs a capability map first

When not to use it

  • Single-line fixes, typo corrections, or changes that are unambiguous and self-contained
  • A spec already exists and you need to slice it into tasks; planning-and-task-breakdown owns that
  • The work is already coded and only needs documentation

How to use it

"/write-the-spec add team billing" → the agent first lists its assumptions, then asks clarifying questions before writing the spec file.

Stops and asks: After saving the spec the agent must end its turn and get human approval before any planning or code.

write-the-domain-glossary

auto-invocable rating 9.7 / A

Sharpens a project's domain model: challenges terms, records them in GLOSSARY.md, offers ADRs for hard-to-reverse decisions, and reviews the prose.

When to use it

  • Discussing or challenging codebase terminology
  • Writing or editing a GLOSSARY.md
  • Recording an architecture decision as an ADR
  • The user's term conflicts with the existing glossary definition
  • The user uses vague or overloaded terms that need one canonical term
  • Domain relationships need stress-testing with concrete scenarios

When not to use it

  • Merely reading GLOSSARY.md to pick up vocabulary; that is a one-line habit, not this skill
  • The decision is easy to reverse, unsurprising without context, or involved no real trade-off: skip the ADR
  • You need to store specs, scratch notes, or implementation details; GLOSSARY.md must hold none of those

How to use it

The user says "account" → the agent asks whether that means the Customer or the User, then writes the resolved term into GLOSSARY.md.

Does not interrupt: It calls out conflicts inline and only offers ADRs, with no approval gate on a destructive action.

document-the-decision

auto-invocable rating 9.7 / A

Records the why behind decisions as ADRs, API docs, README and changelog, matching existing project convention before its own template.

When to use it

  • You keep explaining the same decision repeatedly

When not to use it

  • Documenting obvious code or restating what the code already says
  • Throwaway prototypes
  • Leaving TODO comments or commented-out code instead of doing or deleting it

How to use it

"Document the decision to use PostgreSQL" → the agent inspects the existing ADR convention, then writes context, alternatives and consequences.

Does not interrupt: Documentation-only; nothing destructive is gated.

auto-invocable rating 10 / A

Creates validated architecture, workflow, sequence, dataflow, lifecycle, ERD, class, tree, timeline and waterfall diagrams as standalone interactive HTML, plus one-page explainers; code-backed diagrams trace repository evidence.

When to use it

Plan 3 skills

Cut the work into slices and stress the plan while it is still cheap.

break-into-tasks

auto-invocable stops and asks rating 9.7 / A

Decomposes an approved plan into thin vertical slices with demo lines and dependency order in M###-ROADMAP.md, or GitHub issues after confirmation.

When to use it

  • break this into slices
  • decompose the plan
  • vertical slices
  • break into issues
  • the roadmap's slices are too thick, too few or badly ordered

When not to use it

  • Scope is not signed off yet; it runs only once M###-CONTEXT.md is stable
  • The deliverable is a document or a spike rather than working code, which it explicitly calls not-a-slice

How to use it

"/break-into-tasks on the checkout milestone" → the agent reads M###-CONTEXT.md and the codebase seams, drafts vertical slices with risk and depends, then asks about granularity.

review-the-plan

auto-invocable rating 10 / A

Adversarially reviews a plan or design as junior work, grounds findings in codebase and current sources, then writes a promoted rewrite.

When to use it

  • A plan is ready for sign-off
  • You want the assumptions attacked before they become code
  • A design needs a harder look than its author can give it
  • An agent-generated plan is fog (no interfaces) or tunnel (no product vision)
  • The plan's factual claims need checking against the actual repo

When not to use it

  • The code is already written and only the diff needs reviewing — use review-my-code
  • No plan artifact exists yet — the skill says do not review thin air
  • A one-line fix or typo with no design decisions behind it
  • You need a product direction decided — the skill refuses to invent one

How to use it

"/review-the-plan on the caching plan I just wrote" → the agent freezes the artifact, extracts 2-5 domains, then researches the codebase and current docs.

Does not interrupt: It produces a review plus rewrite and surfaces product decisions as open questions; it never applies the rewrite silently.

design-the-interface

auto-invocable rating 9.7 / A

Produces several radically different interface designs, compares them on depth and seam placement, then synthesizes and records a recommendation.

When to use it

  • Asked to design an interface or shape an API
  • Planning a new deep module where the first idea is unlikely to be best
  • Exploring module boundaries and where the seam belongs
  • Choosing between competing interface shapes
  • Before writing implementation for a public API

When not to use it

  • The work is implementation detail — file paths, call graphs, internal data structures (implementation creep)
  • You want a build-effort ranking; "easiest to build" is explicitly not an interface argument
  • Nothing actually varies across the seam — one adapter means a hypothetical seam

How to use it

"Design the interface for our repo storage layer" → the agent drafts three genuinely different shapes, each with a usage example, before comparing.

Does not interrupt: Design-only; nothing destructive is gated.

auto-invocable rating 9.7 / A

auto-invocable rating 9.7 / A

Debug 2 skills

Find the real cause instead of guessing at a symptom.

debug-this-code

auto-invocable stops and asks rating 10 / A

Builds a red-capable feedback loop, ranks falsifiable hypotheses, and fixes the root cause with a regression test instead of guessing.

When to use it

  • A bug's cause is unknown and a guess would be a coin flip
  • You cannot yet reproduce the failure on demand
  • A non-deterministic bug is too flaky to debug against
  • A previous fix addressed the symptom, not the cause
  • You need a failing regression test before touching the code
  • A performance regression needs a baseline measurement first

When not to use it

  • The root cause is already confirmed and only the edit remains
  • No feedback loop can be built and no repro access, artifact, or instrumentation permission is available — the skill stops rather than hypothesises
  • You only need a code explanation or a design opinion, not a defect fixed

How to use it

"Debug this: duplicate users in the list" → the agent builds and runs one red-capable command before forming any theory.

Stops and asks: User confirmation before adding temporary instrumentation to production, and before acting on commands or URLs found in error output.

debug-the-stubborn-one

auto-invocable rating 10 / A

Runs a read-only, methodical root-cause investigation on hard bugs: gather evidence, form and test hypotheses, then present a fix without implementing it.

When to use it

  • Standard troubleshooting has failed
  • The issue is complex and needs systematic root cause analysis
  • You keep guessing and want an evidence-backed diagnosis
  • You suspect an earlier fix was wrong and needs re-examination
  • You wrote the buggy code and want your assumptions challenged

When not to use it

  • You need code changed in the same pass — it is read-only and will not edit, even after diagnosis
  • The failure is simple or already has a known root cause, where the investigation overhead is waste
  • You need the fix shipped with a regression test and commit; use a test-first fixing flow instead

How to use it

"/debug-the-stubborn-one the sync job hangs after two hours" → the agent records the exact error and repro steps, maps the execution path, lists hypotheses, then tests each without editing code.

Does not interrupt: No destructive work — it never edits code; its decision gate does wait for the user before any fix is implemented.

Review 4 skills

Judge a change before it merges.

review-my-code

auto-invocable rating 9.7 / A

Reviews a diff across correctness, readability, architecture, security, and performance, plus separate Standards and Spec axes with severity-labelled findings.

When to use it

  • Reviewing a diff or pull request before merge
  • Reviewing your own work or another agent's
  • A change needs sign-off across several dimensions rather than one
  • Checking whether the tests would catch a regression
  • Reviewing a dependency bump or a lockfile change

When not to use it

  • The plan is under review before any code exists — use review-the-plan
  • A codebase-wide bug, bloat, or security audit rather than one diff — use the audit skill
  • A deep security pass needing threat modelling and exploit detail — use security-and-hardening

How to use it

"Review my branch against main" → the agent pins the fixed point, confirms the diff is non-empty, then finds spec and standards files.

check-my-security

auto-invocable stops and asks rating 10 / A

Runs a STRIDE and OWASP threat-model review of the code, then reports each finding with a concrete exploit, severity and remediation.

When to use it

  • Before shipping anything that touches auth, input handling, secrets or data storage
  • Review this for security
  • Is this login flow safe
  • We added file uploads, CORS or a new external integration
  • Check dependency and supply-chain risk via the native audit

When not to use it

  • The change touches no auth, input handling, secrets or stored data, so there is no trust boundary to review
  • You want the whole repo audited for bugs, load and bloat rather than security alone
  • You want forced dependency remediation applied for you — it never runs npm audit fix --force automatically

How to use it

"/check-my-security on the new upload endpoint" → the agent maps trust boundaries, walks STRIDE and the OWASP checklist over the actual code, then triages findings by severity x exploitability.

Stops and asks: Adding auth flows, storing new PII, changing CORS, adding upload handlers, altering rate limits or granting roles needs human approval; findings stay private until the user agrees to file them.

receive-code-review

Handles incoming code review feedback with verification and technical pushback instead of performative agreement, clarifying unclear items before implementing.

When to use it

When not to use it

How to use it

"Reviewer says remove the legacy compat shim" → the agent checks the codebase for real callers before editing anything.

audit-the-whole-repo

auto-invocable rating 9.7 / A

Audits a whole repo for bugs, security holes, load failures, untested risky code, slowness and bloat, then returns a ranked plain-English report without changing code.

Verify 4 skills

Produce evidence that it actually works.

prove-it-works

auto-invocable rating 9.7 / A

Blocks any claim that work is complete, fixed, or passing until a fresh verification command has been run and its output read.

When to use it

  • About to claim tests pass, a bug is fixed, or a build succeeds
  • About to commit, push, or open a PR
  • About to move to the next task
  • A subagent or agent reports success
  • You catch yourself writing "should", "probably", or "seems to"

When not to use it

  • No status claim is being made — a question, a read, or a design discussion
  • No verification command exists for the claim, so there is nothing fresh to run and the limitation must be stated instead
  • Relying on a partial check, a previous run, or a linter in place of the compiler

How to use it

"Is the fix done?" → the agent runs the full test command, reads exit code and failure count, then answers.

Does not interrupt: It is a self-imposed evidence gate before claims; it asks no one for approval.

test-every-surface

auto-invocable stops and asks rating 10 / A

Report-only QA for API, CLI, job, worker and webhook surfaces: isolated fixtures, a contract map, retained evidence and a reproducible report. Never fixes bugs.

When to use it

  • Testing an HTTP API, CLI, job, worker or webhook rather than a browser UI
  • Coverage must include invalid input, auth, exit codes, timeouts, retries, idempotency or partial failure
  • On a feature branch without explicit scope, using diff-aware testing of changed and adjacent behavior
  • Replaying a prior functional report in regression mode
  • A reproducible evidence report is required, with findings separated from hypotheses

When not to use it

  • Browser flows: the description routes those to check-my-ui
  • You want the bug fixed or product tests written; this run never edits product code, tests, config or tracked state
  • Production access, destruction or external mutation without permission naming the target, operation and effect
  • A browser target has no documented test framework; report the gap instead of installing anything

How to use it

"/test-every-surface the checkout API" → the agent selects the functional surface, sets up isolated fixtures and announces target, tools and permitted writes.

Stops and asks: Production access, destruction or external mutation needs explicit permission naming the target, operation and effect; unknown ownership blocks the probe.

check-my-ui

auto-invocable stops and asks rating 9.7 / A

Drives a real browser to open the page, click the flow, screenshot it and inspect DOM, console, network and performance.

When to use it

  • Building or debugging anything that runs in a browser
  • Before shipping a change with a visible surface
  • A UI bug needs reproducing in a real browser
  • Console errors or failed network requests need checking
  • Page load, layout shift or interaction performance needs measuring

When not to use it

  • The problem lives in a CLI, job, worker, webhook or API with no browser surface
  • The behaviour is pure logic that a unit test covers faster
  • You need the source code changed: this is a see-and-verify pass, not an implementation skill

How to use it

"Check the checkout page after my CSS change" → the agent opens it in its own tab, screenshots before and after, clicks the flow and inspects console, network and accessibility.

make-it-accessible

auto-invocable rating 9.7 / A

Audits and fixes web accessibility to WCAG 2.1: alt text, contrast, keyboard paths, focus, labels, motion and ARIA.

When to use it

  • Running an a11y audit or WCAG 2.1 compliance pass
  • Keyboard navigation, focus order or visible focus problems
  • Screen-reader semantics, form labels or colour contrast are wrong
  • Before shipping any user-facing surface

When not to use it

  • Non-web UI with no HTML/CSS or ARIA surface — the guidance targets web pages and components
  • Nothing user-facing changes, e.g. a backend-only edit
  • You only want an automated Lighthouse/axe score — the skill still requires manual keyboard, screen-reader, zoom and reduced-motion checks
  • Reference-led design where you plan to copy another product's branding, text, imagery or exact layout — the skill forbids it

How to use it

"/make-it-accessible audit the signup form for WCAG 2.1" → the agent checks labels, alt text, contrast, keyboard path and focus order first.

Does not interrupt: Nothing destructive or irreversible; it edits markup, CSS and JS without an approval gate.

make-it-fast

auto-invocable rating 10 / A

Measures first, fixes only the measured bottleneck, re-measures to keep or revert, then guards the metric against regression.

When to use it

  • Performance requirements exist: load-time budgets or response-time SLAs
  • Users or monitoring report slow behavior
  • Core Web Vitals are below thresholds
  • You suspect a change introduced a performance regression
  • N+1 queries or index problems show up in the query log

When not to use it

  • There is no evidence of a problem yet — premature optimization adds complexity for nothing
  • The re-measured gain sits inside run-to-run noise — that is a revert, not a keep
  • The win requires changing, skipping or deleting a test to land
  • You plan to raise the connection pool without finding what holds connections

How to use it

"/make-it-fast checkout LCP is 4.2s" → the agent captures a Lighthouse baseline, profiles the waterfall, and fixes only the largest bottleneck.

Does not interrupt: Nothing destructive or irreversible; it profiles, edits, and reverts unproven changes itself.

When not to use it

  • Profiling and optimizing measured slowness — use performance-optimization instead

How to use it

"/make-it-observable, we're shipping the payment retry" → the agent first writes the 2-4 questions on-call will ask.

Ship 2 skills

Take it to the remote, or stop something destructive.

ship-it

auto-invocable stops and asks rating 9.7 / A

Verifies tests, detects the git environment and base branch, offers merge, pull request or keep, then commits, pushes and cleans up.

When to use it

  • Implementation is complete and the full test suite passes
  • You need to decide between merging locally and opening a pull request
  • The branch lives in a worktree and cleanup rules must be applied
  • On a detached HEAD and need the reduced push-as-new-branch menu
  • You want the base branch confirmed before merging
  • Pre-commit hygiene: staged-diff check, secrets grep, tests, lint, typecheck

When not to use it

  • Tests are failing: the skill reports the failures and stops, it does not fix them
  • You want to discard the work: that path exists only on an explicit human request, never as a menu option
  • The push was rejected: investigate; force-push only on explicit request
  • A worktree holds uncommitted files only it has: removal is refused, never force it on your own initiative

How to use it

"/ship-it" → the agent runs the full suite, detects the git environment and base branch, then presents the merge/PR/keep menu.

Stops and asks: It waits for the human's menu choice before merging or pushing, and permanent deletion of a branch and worktree needs the human to type "discard".

guard-the-dangerous-stuff

auto-invocable stops and asks rating 9.7 / A

Hand-applied checklist before destructive commands: recursive deletes, DROP/TRUNCATE, force-push, reset --hard, kubectl delete, docker prune, and PowerShell equivalents.

When to use it

  • Before rm -rf, DROP TABLE/DATABASE, TRUNCATE, force-push or git reset --hard
  • Before any command that can destroy data, uncommitted work or production state
  • Before kubectl delete, docker rm -f or docker system prune
  • Before PowerShell/cmd equivalents: ri -r -fo, rd /s, Clear-Disk, irm | iex
  • Before the destructive contract step of a migration

When not to use it

  • Deleting node_modules, dist, .next, __pycache__, build, coverage or .turbo — listed as safe exceptions
  • Read-only inspection, builds or ordinary test runs
  • You expect an automatic intercept — the upstream hook is not installed, this is a written procedure only
  • Deciding whether to deprecate a system at all — that is a product call, answered by the deprecation questions

How to use it

"/guard-the-dangerous-stuff I'm about to git push --force" → the agent checks the pattern table, confirms it targets a non-default branch, and asks for separate authorization.

Stops and asks: Destructive steps must be made explicit and separately authorized (recursive delete, DROP/TRUNCATE, force-push, reset --hard, kubectl delete, docker prune); HIGH-tier shapes are hard-denied.

Meta 6 skills

Change how the session itself runs.

simplify-this-code

auto-invocable rating 9.7 / A

Simplifies code for clarity without changing behavior, one tested change at a time, following project conventions and scoping to recently modified code.

When to use it

  • Refactoring for readability without changing behavior
  • Code works but is harder to maintain than it should be
  • Reviewing code that accumulated unnecessary complexity
  • A proposed simplification would only move the difficulty somewhere else
  • Deep nesting, long functions, nested ternaries, generic names or duplicated logic need cleanup
  • You are about to simplify code whose original purpose you do not yet understand

When not to use it

  • You are also adding a feature or fixing a bug in the same change; refactors must be separate PRs
  • The simplification requires modifying tests to pass, which means behavior changed
  • The code is outside the scope of the current task and you were not asked to broaden scope
  • You cannot answer what the code is responsible for, what calls it, or why it exists (Chesterton's Fence)

How to use it

"Simplify this function" → the agent checks git blame, callers and the defining tests, then makes one change and runs the suite.

Does not interrupt: No destructive action is gated; it reverts a change when tests fail rather than asking for approval.

split-across-agents

auto-invocable rating 9.7 / A

Runs independent tasks in parallel subagents with focused, self-contained prompts, then reviews, integrates and runs the full suite on what returns.

When to use it

  • 3+ test files fail with different root causes
  • Multiple subsystems are broken independently
  • Each problem can be understood without context from the others
  • No shared state between investigations
  • A large job can be dispatched instead of done inline
  • Each dispatched agent can get one scope, one goal, constraints and an expected output

When not to use it

  • Failures are related, so fixing one might fix others; investigate together first
  • Understanding the problem requires seeing the full system state
  • Exploratory debugging where you do not yet know what is broken
  • Agents would interfere by editing the same files or using the same resources

How to use it

"/split-across-agents" → the agent groups the failures into independent domains and dispatches one focused subagent per domain in one response.

Does not interrupt: No destructive action is gated; returned work goes through a review-and-integrate gate instead.

hand-off-to-next-session

auto-invocable rating 9.7 / A

Writes a tight continue.md in the active slice and refreshes STATE.md and summaries so a fresh session resumes in one minute.

When to use it

  • Context budget is running low mid-task
  • Before a risky operation such as a dependency upgrade or major refactor
  • End of a long multi-day session with unfinished work

When not to use it

  • You want a chat recap of the journey — the next agent doesn't need it
  • Nothing is in flight and no concrete next action exists

"/hand-off-to-next-session I'm out of context" → the agent writes the last action, one concrete next action, and what not to do into continue.md.

watch-my-context

auto-invocable rating 10 / A

Installs a per-turn canary line (name, turn counter, self-check) so context degradation shows immediately, and runs a checkpoint-and-re-anchor recovery protocol when it trips.

When to use it

  • Starting a long or high-stakes session and wanting an early-warning signal
  • The user mentions a canary, context canary, or canary check
  • The user notices the canary stopped appearing and asks what happened
  • The agent can no longer find the canary contract in its own context
  • The user asks how trustworthy the current context still is

When not to use it

  • You want a check that survives compaction across all sessions: a standing canary in CLAUDE.md or agent memory measures only file-based instruction attention, a weaker signal
  • You want structural assurance that harder constraints (architecture decisions, never-touch rules) still hold; a present canary is only weak evidence of health
  • You expect a positive canary to prove context is fine; the test is one-sided and only a missing canary is strong evidence

How to use it

"/watch-my-context" → the agent states the contract "Julius · t1 · ctx ok" and prefixes every later reply with it.

Does not interrupt: It recommends a fresh session and asks the user's name if unknown, but gates no destructive action.

What this page does not claim

  • Guidance is derived, not quoted. The prose above condenses each skill's own text. The skill body is the authority; this page is an index. Skill bodies are immutable in this repo and are proven against upstream with tools/verify.py.
  • Only 13 of the 42 ship an explicit “When to Use” heading, and just one ships a “When not to Use” heading. The negative guidance here is assembled from each skill's stated exclusions, red flags and hard constraints. Where a skill states none, the entry is limited to what its text clearly supports rather than invented.
  • The approval model is the harness's, not the skill's. Changing the session preset changes every row of the approval picture at once. A skill's written gate is a instruction to the agent, not an enforced intercept.
  • Skill names are directory names under skills/. Invoke one with the skill tool or by typing /name.
